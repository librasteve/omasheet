# Design: widen what lowers to Polars

Forthcoming. D numbers are assigned when the change starts; `D-W#` until then.

|---|--------|----------|-------|
| D-W1 | Settled (1) | A column lowers only if every operand's type is one the checker knows: a declared column type, a type inferred from all of the column's cells, or the type of a literal, a constant or a function result | The inference runs when the column is loaded (`check.rs`, `join`), so an undeclared column has a static type as much as a declared one; nothing is looked at again when a plan is made. The dress of a result (`Percent`, a unit, an uncertainty) is the checker's, taken once; Polars does the numbers |
| D-W2 | Settled (1) | A column typed `Fraction` or `Any`, which includes a column of mixed types, is never lowered. A `String` column still lowers, for the tests a filter is written with (D177). ## Quantity and Scientific with `Any`

`Quantity op Quantity` lowers because the unit work is a meta-operation: the checker works out the result's dimension and unit once, and the factor between two units of one dimension is a constant, so Polars only has to multiply, add or divide the numbers, as it already does for `Decimal`. Offset units (`°C`) need an affine step and stay on the engine until the engine's rule for them is checked. A `Scientific` is a value with an uncertainty, which the Parquet form already keeps as separate fields, so `Scientific op` a number or another `Scientific` can lower as two `Float64` expressions, the value and the propagated uncertainty, whose formulas must match the engine's operation by operation. `Scientific op Any` is different: `Any` has no static type, so the checker cannot choose a lowering, and mapping every uncertain form of every operation onto `apply`-style per-row callbacks would only reproduce the engine's per-row evaluation inside Polars, losing parallelism and optimisation and adding conversion cost for no speed. **Recommendation:** lower `Quantity` and `Scientific` operations when both operand types are static and the unit rules are simple; leave anything involving `Any` on the engine; do not build a per-row bridge (D-W7).

## Open items, settled (0.2)

- **Sigma tolerance (D-W5): exact on the value, within 4 ulps on the sigma.** Polars has no `hypot`, so the lowered sigma is `sqrt(a² + b²)` (with `sqrt` turned on, below), which can differ from the engine's `hypot` in the last place. The agreement test compares the value bit for bit and the sigma to 4 ulps; a lowered column is not believed where it differs by more, and the engine calculates it.
- **Polars features: more may be turned on.** In the workspace `Cargo.toml` (now `lazy`, `abs`, `cum_agg`, `diff`, `rank`, `rolling_window` and the dtype set) where a lowering needs them: `sqrt` and `pow` for the sigma of `*` and `/`, and `floor`, `pow` and `log` for `%` and `**` of a `Scientific`. Each feature is added in the task that needs it, with its cost in build time noted there, and a lowering that needs one stays on the engine until it is on. This lifts the stated reason for `%` and `**` staying on the engine in D-W5; whether they then lower is for task 3.4 to decide on the exactness of the agreement test. The feature names are not yet checked against Polars 0.51.
- **A `const` is read as a value, not inlined by the checker.** `lower.rs` reads `Ir::Const(i)` through `(cx.constant)(i)` and `lit_of`, which declines a `Value::Percent` (`lit_of` has no arm for it) the same way `Lit::Percent` is declined. D-W3 is applied in the lowerer, in both places: the `Lit::Percent` arm and the `Ir::Const` arm turn a percentage into the `Decimal` it is, and the dress of the result is the checker's, by `S::wider`. No change to `check.rs` is needed. `examples/budget.omx` (`Tax := Profit * TaxRate`) is the first test.
- **A declared `Percent` column is not the inferred case.** Its static type is `Percent`, so it lowers as the `Decimal` it is. A mix of a bare number and a percentage arises in an expression (`Rate * 2`, `Rate + 2%`), and `S::wider` fixes its dress from the static types: two percentages a percentage, any other mix the plain number. What stays declined is a column with *no declared type* whose cells differ in dress (D-W1). I have not re-read D69a's own wording: task 2.3 (`Rate * 2`, `Rate + 2%`, `5% + 3%`) is the check, and if the engine disagrees the case is added to the declined list there.

## Risks

- A formula that differs from the engine's in the last digit: every case is gated by an agreement test, and a lowered column is not believed where the two disagree.
- A column whose declared type is wrong for its values: the checker catches it where the column is read in, and the engine calculates it as it does now.
